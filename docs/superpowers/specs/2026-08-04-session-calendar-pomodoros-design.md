# Помидорки из календаря Session — дизайн

## Мотивация

Фокус-сеансы уже трекаются приложением [Session](https://www.stayinsession.com/), которое пишет каждый завершённый сеанс отдельным событием в свой календарь Apple. В трекере те же помидорки набиваются руками кнопками `+1` / `−1` — двойной учёт, который к вечеру расходится.

Задача: одной кнопкой перенести счёт из календаря в поле `Day.pomodoros`. Читать календарь есть чем — `backend/src/icloud/` уже логинится в iCloud CalDAV через `tsdav` для GTD-напоминаний, теми же учётными данными (`ICLOUD_APPLE_ID` + пароль приложения) доступен и календарь Session, если он синкается в iCloud.

## Решения (зафиксировано на брейншторме)

- **Только кнопка, никакого фонового синка.** Бэкенд ходит в календарь исключительно по явному клику пользователя. Отвергнут вариант с `setInterval` каждые 5 минут: он молча перезаписывал бы счётчик в произвольный момент, в том числе затирая ручные правки, и держал бы постоянный сетевой трафик к iCloud ради поля, которое меняется несколько раз в день.
- **Календарь — источник правды в момент нажатия.** Кнопка ставит `pomodoros = N`, а не прибавляет. Перезапись безопасна именно потому, что она случается по клику: пользователь сам выбирает, когда календарь важнее того, что он накликал руками. Ручные `+1` / `−1` / `сбросить` продолжают работать как раньше и живут до следующего нажатия кнопки.
- **Одна помидорка = одно событие длиннее порога.** Порог в минутах задаётся `SESSION_MIN_MINUTES` (по умолчанию 20) и отсекает перерывы и оборванные сеансы, если Session пишет их в тот же календарь. Отвергнута «сумма минут / 25»: часовой сеанс — это один непрерывный фокус, а не две помидорки, и такой подсчёт разошёлся бы с тем, что человек видит в самом Session.
- **Выключено по умолчанию.** Нужны одновременно `ICLOUD_APPLE_ID`, `ICLOUD_APP_PASSWORD` и `SESSION_CALENDAR_NAME`. Без них кнопки в интерфейсе нет вовсе, а панель помидорок выглядит ровно как сейчас — трекер остаётся полностью рабочим с ручным счётчиком. Это тот же env-gated паттерн, что у `obsidian/`, `icloud/` и `telegram/`.
- **Ошибка никогда не обнуляет день.** Ноль записывается только если календарь реально ответил и подходящих событий в нём нет. Сетевой сбой, ненайденный календарь, нераспарсенный ICS — это ошибка ответа, а не «ноль помидорок».
- **Только чтение.** Трекер ничего не пишет в календарь Session и не создаёт там события.

## Архитектура

### Выделение CalDAV-клиента

`ICloudService` сейчас совмещает две несвязанные обязанности: логин в CalDAV с кэшированием клиента и работу с VTODO-напоминаниями GTD. Календарь Session — другой ресурс (VEVENT, только чтение), и дублировать логин ради него не нужно.

Новый файл `backend/src/icloud/caldav.client.ts`:

```ts
@Injectable()
export class CalDavClient {
  hasCredentials(): boolean;
  // null, если кредов нет или логин не удался
  getClient(): Promise<DAVClient | null>;
  // null, если календаря с таким displayName нет; результат кэшируется по имени
  findCalendar(name: string): Promise<DAVCalendar | null>;
}
```

Поведение переносится из `ICloudService` без изменений, включая важную деталь: `this.client` присваивается только после успешного `login()`, чтобы следующий вызов повторил попытку, а не переиспользовал навсегда неаутентифицированный экземпляр. Кэш календарей становится `Map<string, DAVCalendar>` — теперь их два (список напоминаний GTD и календарь Session).

`ICloudService` после рефакторинга берёт клиент и календарь у `CalDavClient`, его публичный API (`syncReminder`, `completeReminder`, `removeReminder`, `syncAllOnStartup`) не меняется — существующие тесты `icloud.helpers.spec.ts` остаются в силе.

`ICloudModule` экспортирует и `ICloudService`, и `CalDavClient`.

### Новый модуль `backend/src/session/`

- `session.helpers.ts` — чистые функции, без сети и без Nest:
  ```ts
  export interface CalendarEvent { start: Date; end: Date }
  // Разбор одного VCALENDAR: DTSTART/DTEND/DURATION, UTC-форма, TZID, VALUE=DATE
  export function parseEvents(ics: string): CalendarEvent[];
  // Границы суток даты в указанном поясе, как абсолютные моменты
  export function dayWindow(date: string, timeZone: string): { start: Date; end: Date };
  // События, пересекающиеся с окном и длящиеся >= minMinutes
  export function countPomodoros(events: CalendarEvent[], window: {start: Date; end: Date}, minMinutes: number): number;
  ```
- `session.service.ts` — `syncDate(date: string): Promise<number | null>`: берёт календарь через `CalDavClient.findCalendar(SESSION_CALENDAR_NAME)`, тянет объекты за диапазон, парсит, считает. Число — успех, `null` — любая ошибка чтения (никогда не бросает). Плюс `isEnabled(): boolean` для проверки конфигурации.
- `session.module.ts` — импортирует `ICloudModule`, экспортирует `SessionService`.

`SessionModule` импортируется в `DaysModule` — контроллер дней его единственный потребитель. В `app.module.ts` он попадает транзитивно, отдельной записи не нужно.

### Эндпоинт

```
POST /days/:date/pomodoros/sync-session  ->  DayView
```

Обработчик в `DaysController` рядом с существующим `PATCH /days/:date/pomodoros`:

1. Интеграция выключена (нет кредов или пустой `SESSION_CALENDAR_NAME`) → `409 Conflict`, `"Синхронизация с календарём Session не настроена"`.
2. `SessionService.syncDate(date)` бросил или вернул `null` (календарь не найден, сеть, разбор) → `502 Bad Gateway`, `"Не удалось прочитать календарь Session"`. Счётчик не трогается.
3. Успех → `DaysService.setPomodoros(date, count)` и обычный `DayView` в ответ.

Новый метод в `DaysService` рядом с `updatePomodoros` (`days.service.ts:116`):

```ts
async setPomodoros(dateStr: string, count: number): Promise<DayView>
```

Он ставит абсолютное значение, а не дельту. Существующий `updatePomodoros` не трогаем: его контракт (`delta` / `reset`, где `reset` перебивает `delta`) уже используется фронтом и iOS-шорткатами.

### Признак «интеграция включена» для фронта

`GET /settings` дополняется вычисляемым полем `sessionSyncEnabled: boolean`. В БД оно не хранится и в `PATCH /settings` не принимается — это отражение env, а не пользовательская настройка. `SettingsService.get()` подмешивает его к записи из БД, беря значение из `SessionService.isEnabled()` (`SettingsModule` импортирует `SessionModule`), чтобы правило «включено» жило в одном месте.

### Фронтенд

- `frontend/lib/api.ts`: `syncSessionPomodoros(date: string): Promise<DayView>`.
- `frontend/types/api.ts`: поле `sessionSyncEnabled` в типе настроек.
- `frontend/components/PomodoroPanel.tsx`: новые пропсы `onSyncSession?: () => void` и `syncing: boolean`. Рядом со ссылкой `сбросить` появляется ссылка `из Session`; если `onSyncSession` не передан — не рендерится вовсе. Во время запроса ссылка дизейблится (CalDAV отвечает за секунду-две), текст ошибки показывается под счётчиком.
- `frontend/components/Dashboard.tsx`: функция `syncSession()` по образцу `addPomodoro` / `resetPomodoro` (`Dashboard.tsx:181`) — вызывает API и кладёт ответ в `setDay`. Проп передаётся в `PomodoroPanel` только когда `settings.sessionSyncEnabled`.

`DayDetailModal` не трогаем: подтягивание задним числом за произвольную дату в этой итерации не нужно, эндпоинт при этом принимает любую дату и остаётся доступен из курла.

## Часовые пояса

Трекер живёт по UTC: `parseDateParam` строит полночь UTC, `todayDate()` берёт UTC-дату (`backend/src/common/date.util.ts`), контейнер бэкенда стартует без `TZ`. Session же пишет события в локальном поясе пользователя. Если считать окно суток в UTC, при UTC+3 все сеансы после 21:00 попадут в следующий день.

Решение: окно считается в поясе `process.env.TZ` (по умолчанию `UTC`), а в `docker-compose.yml` добавляется `TZ: ${TZ:-UTC}`, чтобы пояс задавался из корневого `.env` (`TZ=Europe/Moscow`). `dayWindow()` получает пояс параметром, поэтому тестируется без переменных окружения.

Существующая UTC-семантика дат в остальном трекере намеренно не трогается — это отдельная задача, задевающая всю историю дней.

## Конфигурация

Новые переменные в `.env.example` и в `docker-compose.yml` (через `${VAR:-default}`, как уже сделано для iCloud и Telegram):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `SESSION_CALENDAR_NAME` | пусто | `displayName` календаря Session в iCloud. Пусто = интеграция выключена |
| `SESSION_MIN_MINUTES` | `20` | Событие короче не считается помидоркой |
| `TZ` | `UTC` | Пояс, в котором считаются границы суток |

Учётные данные переиспользуются: `ICLOUD_APPLE_ID`, `ICLOUD_APP_PASSWORD`.

## Разбор ICS

Из `VEVENT` нужны только границы. Форматы, которые надо покрыть:

- `DTSTART:20260804T093000Z` — UTC, парсится напрямую.
- `DTSTART;TZID=Europe/Moscow:20260804T123000` — локальное время в именованном поясе.
- `DTSTART;VALUE=DATE:20260804` — событие на весь день. Такие события пропускаются: сеанс Session всегда имеет время, а «весь день» дал бы ложную помидорку в 24 часа.
- `DTEND` отсутствует, есть `DURATION:PT25M` — конец вычисляется как начало плюс длительность.
- Ни `DTEND`, ни `DURATION` — событие пропускается (нулевая длительность всё равно не прошла бы порог).

Строки со сложенными продолжениями (RFC 5545 folding: перевод строки плюс пробел) разворачиваются перед разбором. Повторяющиеся события (`RRULE`) не разворачиваются — Session пишет разовые события; если такое встретится, засчитается только исходное вхождение. Это осознанное ограничение, а не баг.

Событие засчитывается, если оно **пересекается** с окном суток и его длительность `>= SESSION_MIN_MINUTES`. Сеанс, начатый в 23:50 и законченный в 00:20, засчитывается в оба дня — это редкий случай, и такое поведение предсказуемее, чем привязка к моменту старта.

## Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Нет `ICLOUD_*` или `SESSION_CALENDAR_NAME` | Кнопки во фронте нет; эндпоинт отвечает `409` |
| Логин в iCloud не удался | `logger.warn`, `502`, счётчик не тронут |
| Календарь с таким именем не найден | `logger.warn` с именем, `502`, счётчик не тронут |
| Запрос объектов упал / таймаут | `logger.warn`, `502`, счётчик не тронут |
| Календарь ответил, событий нет | `pomodoros = 0` — это валидный результат |
| Отдельный `VEVENT` не распарсился | Пропускается, остальные считаются; `logger.debug` |

Пароль приложения не должен попадать в текст ошибки: сообщения логируются как `String(e)`, поэтому в `session.service.ts` применяется та же защита, что в `telegram.service.ts:40` — вырезание секрета из строки перед логированием.

## Тестирование

**`session.helpers.spec.ts`** (чистые функции, без сети):
- `parseEvents`: UTC-форма, `TZID`, `DURATION` вместо `DTEND`, `VALUE=DATE` (пропуск), событие без конца (пропуск), несколько `VEVENT` в одном ответе, свёрнутые строки.
- `dayWindow`: `Europe/Moscow` даёт границы 21:00 UTC предыдущих суток и 21:00 UTC текущих; `UTC` даёт полночь-полночь.
- `countPomodoros`: порог отсекает 15-минутное событие и пропускает 25-минутное; событие целиком вне окна не считается; событие через полночь считается в обоих окнах; пустой список даёт 0.

**`session.service.spec.ts`** (`CalDavClient` замокан):
- нет `SESSION_CALENDAR_NAME` → `syncDate` не делает запросов;
- календарь не найден → возвращает `null`, не бросает;
- запрос упал → возвращает `null`;
- пустой ответ → `0`;
- три подходящих события → `3`.

**`days.service.spec.ts`** (дополняется): `setPomodoros` ставит абсолютное значение и не зависит от предыдущего.

**`days.controller`**: `409` при выключенной интеграции, `502` при `null` от сервиса, `DayView` при успехе.

**Фронт** (`frontend/lib/api.spec.ts`): `syncSessionPomodoros` шлёт `POST` на верный путь и отдаёт разобранный `DayView`. Тестов на сам компонент не будет: в проекте нет `@testing-library/react`, а `jest.config.js` матчит только `.spec.ts` — рендер-тесты потребовали бы новых зависимостей и отдельного окружения, что несоразмерно одной ссылке в панели.

## Что не входит

- Обратная запись в календарь Session.
- Автоматический фоновый синк по расписанию.
- Кнопка в `DayDetailModal` для прошлых дней.
- Разворачивание повторяющихся событий.
- Изменение UTC-семантики дат в остальном трекере.
