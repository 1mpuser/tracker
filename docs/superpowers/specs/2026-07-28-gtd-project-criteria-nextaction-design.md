# GTD — критерии проекта + выделение next action — дизайн

## Мотивация

Карточка проекта (`ProjectCard.tsx`) сейчас показывает шаги плоским списком без выделения «что делать дальше», а «критерии окончания» и «с кем обсудить» — это просто общий текст в `notes`, ничем не отделённый от прочих заметок. Это два из трёх пунктов исходного пайплайна разбора проекта («декомпозировать / с кем обсудить / критерии / первый шаг») из `docs/superpowers/specs/2026-07-23-gtd-core-design.md`, реализованные пока лишь как договорённость, а не как структура. Декомпозиция (кнопка «добавить шаг», по одной задаче за раз) уже работает как задумано и не меняется.

## Решения (зафиксировано на брейншторме)

- **Критерии окончания** и **с кем обсудить** — два отдельных текстовых поля, не чек-лист, не структура. Существуют только у проектов (`status = project`); у обычных пунктов не показываются.
- **Next action** — не новое поле, вычисляется на лету: первый по `order` дочерний пункт со `status = backlog`. Шаги в `waiting`/`calendar`/`someday`/`done` кандидатами не считаются — они уже понятны по своему статусу («в ожидании», «запланировано» и т.д.), next action должен указывать именно на то, что реально надо взять и сделать прямо сейчас.
- Подсветка next action видна **только внутри открытой `ProjectCard`** — ни в общем списке «Проекты», ни где-либо ещё.
- Заодно поле `notes` проекта (сейчас read-only текст в карточке) становится редактируемым прямо в карточке — иначе будет нелогично: два новых поля редактируются инлайн, а соседнее старое — нет.

## Модель данных

Два additive nullable-поля, миграция `add_gtd_project_fields`:

```prisma
model GtdItem {
  // ...
  acceptanceCriteria String?
  discussWith        String?
}
```

## Backend

- `UpdateGtdItemDto`: `acceptanceCriteria?: string`, `discussWith?: string` (`@IsOptional() @IsString()`, по образцу `notes`/`waitingFor`).
- `GtdItemView`: `acceptanceCriteria: string | null`, `discussWith: string | null`. `toView()` мапит оба.
- `GtdService.update`: присвоение как у `notes`/`waitingFor` — без побочных эффектов (не участвуют в `effectiveDue`, не триггерят iCloud/Obsidian синки).
- `CreateGtdItemDto` не меняется — поля заполняются после создания, PATCH'ем из карточки.

## Frontend

- `types/api.ts`: `GtdItem` получает `acceptanceCriteria: string | null`, `discussWith: string | null`.
- `lib/api.ts` / `updateGtdItem` — `Pick` расширяется `'acceptanceCriteria' | 'discussWith'`.
- `GtdScreen.tsx`: `onUpdate`-Pick-тип расширяется теми же двумя ключами (плюс уже используемый `notes`, если ещё не входит в список для проектных правок из карточки).
- `lib/gtd.ts`: чистая функция

  ```ts
  function nextActionId(children: GtdItem[]): number | null {
    const backlog = children.filter(c => c.status === 'backlog').sort((a, b) => a.order - b.order);
    return backlog[0]?.id ?? null;
  }
  ```

  Покрывается TDD-спекой: пустой список → `null`; все шаги вне backlog → `null`; есть backlog-шаги → id первого по `order`; вход не мутируется.

- `ProjectCard.tsx`:
  - Шаг с `id === nextActionId(children)` получает акцент (класс `styles.stepNext`, подпись «Следующее»/бейдж) в списке шагов.
  - Под заголовком — три инлайн-редактируемых текстовых поля вместо нынешнего read-only `notes`: **Заметки** (`notes`, уже существует, становится editable), **Критерии окончания** (`acceptanceCriteria`), **С кем обсудить** (`discussWith`). Каждое — textarea/input, сохранение по blur через `updateGtdItem(project.id, { <field>: value })`.
  - После сохранения любого поля карточка обновляет собственное локальное состояние `project` (а не только фоновый список через `onChanged()`) — иначе поля откатятся к старым значениям до закрытия/переоткрытия карточки. Проще всего: `ProjectCard` держит редактируемые поля в собственном `useState`, инициализированном из `project`, и не зависит от father-компонента для отображения актуальных значений после сохранения.
  - `GtdScreen.tsx`: `openProject` синхронизируется после `onChanged()` — если открытый проект есть в свежем списке `items`, `openProject` обновляется на актуальную версию (по `id`), чтобы при повторном открытии/перерендере карточка не показывала протухшие данные.

## Тесты (TDD)
- **Backend** (`gtd.service.spec.ts`): `update` с `acceptanceCriteria`/`discussWith` (запись, включая очистку пустой строкой/`null`, по аналогии с `notes`); `getItems`/`getForDate` отдают оба поля через `toView`.
- **Frontend** (`lib/gtd.spec.ts`): `nextActionId` — все перечисленные выше случаи.
- Компоненты (`ProjectCard`) — гейт `bun run build`, как и остальной UI-код проекта (юнит-тестами не покрываются по конвенции).

## Не входит в объём
- Чек-лист/структурированные критерии — только текст.
- Подсветка next action где-либо кроме открытой `ProjectCard` (список «Проекты», «Сегодня» и т.д.).
- Критерии/«с кем обсудить» у не-проектных пунктов.
- Изменение механизма декомпозиции («добавить шаг») — остаётся как есть.
