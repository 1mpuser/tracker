# GTD — семантика бакетов и принудительный разбор — дизайн

Дата: 2026-08-12

## Мотивация

Пользователь не различает бакеты «Бэклог» и «Когда-нибудь»: на шаге воронки «Когда?» выбор между «В ближайшее» и «Когда-нибудь» делается наугад. Замер состояния базы на 2026-08-12:

| Бакет | Шт. | Симптом |
|---|---|---|
| `backlog` | 13 | 6 задач лежат с 19–25.07 без единого касания |
| `someday` | 6 | все созданы 26–27.07, движения нет |
| `calendar` | 6 | даты 25.07, 28.07, 06.08 прошли, задачи живы |
| `inbox` | 4 | старейшая от 26.07 — ежедневный разбор не выполняется |

Задача «прибраться в квартире» существует в четырёх экземплярах (`calendar` 28.07; `backlog` «закончить уборку в квартире»; плюс перезаписана заново 11.08 и 12.08) — пользователь не доверяет системе и записывает заново вместо поиска.

Корневая причина — не формулировки, а отсутствие форсирующей функции: ни один бакет не требует пересмотра, поэтому и `backlog`, и `someday` выродились в свалку, а выбор между ними стал произвольным. Воскресный `WeeklyReview` — чеклист с галочками «я посмотрел», он не требует решений по конкретным задачам.

## Решения (зафиксировано на брейншторме 2026-08-12)

- **«В ближайшее» = горизонт «эта неделя»**, а не «готово к работе». Разделитель между бакетами — срок, а не состояние задачи.
- **Переименование в UI** (enum в БД не трогаем, миграция статусов не нужна):
  - `backlog` → «Бэклог недели»
  - `someday` → «Потом»
  - вопрос воронки «Когда?» → «Когда будешь делать?», ответы: «На дату → Календарь» / «На этой неделе» / «Потом»
- **Протухание**: задача в `backlog`, по которой больше 7 дней не было решения, помечается протухшей. Ничего не переезжает автоматически — система помечает и требует решения.
- **Просрочка**: задача в `calendar` с `scheduledDate` в прошлом — сломанная договорённость, разбирается ежедневно.
- **Разделение ритмов**:
  - просроченные — **ежедневно**, без лимита (их по определению мало);
  - протухшие — **в воскресном обзоре**, разбираются по одной прямо в модалке.
- **Дубли**: при вводе в поле захвата показываются похожие живые задачи. Предупреждение, не блокировка.
- Приоритеты, оценки, повторяющиеся рутины — вне объёма (см. «Не входит в объём»).

## Модель данных

Новое поле в `GtdItem`:

```prisma
decidedAt DateTime?
```

`updatedAt` для этого не годится: правка заголовка или заметки сбросила бы счётчик протухания. `decidedAt` — момент последнего **решения о судьбе** задачи.

**Кто ставит.** `GtdService.update()`: если в патче присутствует `status` (даже если значение совпадает с текущим) — `data.decidedAt = new Date()`. Совпадающий статус тоже обновляет поле намеренно: кнопка «Беру» в обзоре шлёт `{ status: 'backlog' }` и продлевает жизнь задачи без отдельного эндпоинта.

**Бэкфилл существующих строк.** Миграция проставляет `decidedAt = createdAt` для всех существующих записей. Это консервативно и честно: шесть залежавшихся задач бэклога сразу покажутся протухшими — что соответствует реальности.

**Точность.** Поле — полный `DateTime` (не `@db.Date`), сравнение на фронте идёт с точностью до дня. Расхождение часовых поясов в пределах часов на пороге в 7 суток значения не имеет.

`GtdItemView` и `frontend/types/api.ts` получают `decidedAt: string | null` (ISO-строка либо `null`).

## Чистые функции — `frontend/lib/gtd.ts` (TDD)

```ts
lastDecisionDate(item: GtdItem): string | null
```
Максимум из даты `decidedAt` (дневная часть ISO) и `plannedDate`. Учёт `plannedDate` обязателен: задача, которую недавно вытягивали в «сегодня», находится в работе, а не гниёт. Проверка на реальных данных: «Сходить в качалку» (`plannedDate` 08.08) — живая; «позаниматься футболом» (без `plannedDate`, с 24.07) — протухшая.

```ts
isStale(item: GtdItem, today: string): boolean
```
`status === 'backlog'` И разница между `today` и `lastDecisionDate` ≥ 7 дней. Если обеих дат нет — считается протухшей (консервативно).

```ts
isOverdue(item: GtdItem, today: string): boolean
```
`status === 'calendar'` И `scheduledDate < today`.

```ts
overdueItems(items: GtdItem[], today: string): GtdItem[]
staleItems(items: GtdItem[], today: string): GtdItem[]
```
Отфильтрованные списки, отсортированные от самых старых.

```ts
staleDays(item: GtdItem, today: string): number
```
Возраст решения в днях — для бейджа.

```ts
findSimilar(title: string, items: GtdItem[], limit = 3): GtdItem[]
```
Нормализация (нижний регистр, обрезка, схлопывание пробелов), затем совпадение по значащим словам (слова длиной ≥ 4 символов; совпало хотя бы одно). Ищет только среди живых задач (`status` не `done`/`archived`). Возвращает не более `limit`. Тесты строятся на реальных четырёх «уборках»: «прибраться в квартире» находит «Прибраться в квартире» и «закончить уборку в квартире».

## Ежедневный разбор — `InboxProcessor`

Вкладка `inbox` называется **«Разбор»** и работает в два акта:

1. **Входящие** — существующая воронка, без изменений.
2. **Просроченные** — блок появляется, когда входящих не осталось. Показываются все просроченные, по одной:

   > «Дата 06.08 прошла. Что с ней?»
   > `Новая дата` · `В бэклог недели` · `Архив`

   - `Новая дата` → `{ status: 'calendar', scheduledDate: <новая> }` (инлайновый `DatePicker`, как в существующем `datePick`)
   - `В бэклог недели` → `{ status: 'backlog', scheduledDate: null, scheduledTime: null }` — дату обязательно чистим, иначе останется мусорный `scheduledDate`, как сейчас у «закончить уборку в квартире» (в `backlog`, но с `scheduledDate` 27.07)
   - `Архив` → `{ status: 'archived' }`

Компоненту нужен полный список задач (сейчас приходят только `inbox`), поэтому `GtdScreen` передаёт дополнительный проп `allItems: GtdItem[]`; `items` остаётся входящими.

Поле захвата под инпутом показывает результат `findSimilar` от текущего значения: `Похоже, уже есть: «прибраться в квартире» → открыть`. Клик переключает на бакет задачи. Ничего не блокирует, Enter работает как раньше.

## Воскресный обзор — `WeeklyReview`

Модалка перестаёт быть чеклистом «я посмотрел» и начинает требовать решений.

- Компонент получает проп `items: GtdItem[]` и `today: string` от `GtdScreen`.
- Шаг «Бэклог» переименован в «Бэклог недели», к нему добавляется счётчик протухших (`протухло: 6`).
- При наличии протухших шаг разворачивается в разбор по одной задаче прямо в модалке:

  > «позаниматься футболом» — лежит 19 дней. Берёшь на этой неделе?
  > `Беру` · `Потом` · `Архив` · `На дату`

  - `Беру` → `{ status: 'backlog' }` (обновляет `decidedAt`)
  - `Потом` → `{ status: 'someday' }`
  - `Архив` → `{ status: 'archived' }`
  - `На дату` → инлайновый `DatePicker` → `{ status: 'calendar', scheduledDate }`

- Шаг «Когда-нибудь» переименован в «Потом», формулировка подсказки — «Поднять что-то в Бэклог недели?».
- Шаг считается пройденным, когда протухших не осталось; галочка вручную по-прежнему доступна для шагов без очереди.
- Модалке нужен колбэк `onChanged`, чтобы `GtdScreen` перезагружал список после каждого решения.

## Отображение — `GtdItemRow`

- В бакете `backlog` протухшая задача получает бейдж возраста (`19д`) в приглушённо-тревожном цвете из существующих токенов (`--accent-glow` / стиль `.overdue`, уже используемый для `dueDate`).
- В бакете `calendar` просроченная `scheduledDate` красится тем же классом `.overdue`, что и просроченный `dueDate` (сейчас `scheduledDate` рисуется нейтрально — `GtdItemRow.tsx:186`).
- Новых кнопок в строке не появляется: все решения принимаются в разборе.

## Вкладки — `frontend/lib/gtd.ts`

`BUCKET_TABS`: `inbox` → «Разбор», `backlog` → «Бэклог недели», `someday` → «Потом». Остальные подписи без изменений. Пустые состояния в `GtdScreen.emptyMessage` приводятся к новым названиям.

## iCloud

Синк с Напоминаниями уже реализован (`backend/src/icloud/`, креды в env) и реагирует на изменения в `GtdService.update()` (`gtd.service.ts:113–122`), поэтому отдельной работы не требует. Проверка последствий наших решений:

- `Новая дата` → `effectiveDue` не пуст → `syncReminder` обновляет VTODO.
- `В бэклог недели` → статус больше не `calendar`, `scheduledDate` очищен → `effectiveDue` пуст, а до правки был не пуст → `removeReminder`.
- `Архив` → то же самое, напоминание удаляется.

Изменение `decidedAt` на `effectiveDue` не влияет — лишних обращений к CalDAV не возникает.

## Тесты (TDD)

Фронт (`frontend/lib/gtd.spec.ts`, jest):
- `lastDecisionDate` — берёт максимум; `plannedDate` перевешивает более старый `decidedAt`; оба `null` → `null`.
- `isStale` — ровно 7 дней = протухла, 6 дней = нет; не `backlog` → всегда `false`; свежий `plannedDate` спасает старую `decidedAt`.
- `isOverdue` — вчерашняя дата да, сегодняшняя нет; только для `calendar`.
- `staleDays` — счёт в днях.
- `findSimilar` — находит регистровые и словоформенные дубли «уборки»; не находит несвязанное; исключает `done`/`archived`; не возвращает саму себя при редактировании; уважает `limit`.

Бэк (`backend/src/gtd/gtd.service.spec.ts`):
- `update` со `status` в патче проставляет `decidedAt`.
- `update` со `status`, равным текущему, всё равно обновляет `decidedAt` (сценарий кнопки «Беру»).
- `update` без `status` (правка заголовка) не трогает `decidedAt`.
- `toView` отдаёт `decidedAt` в ISO либо `null`.

## Не входит в объём

- Автоматический переезд задач между бакетами без участия пользователя.
- Жёсткий лимит на размер бэклога.
- Повторяющиеся рутины («прибраться в квартире», «сходить в качалку» записываются заново каждую неделю — это отдельная функция, не GTD-задачи).
- Изменение enum `GtdStatus` в базе.
- Работы по iCloud — синк уже реализован.
- Приоритеты, оценки времени, дедлайны — существующие поля не трогаем.
