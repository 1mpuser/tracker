# Многопользовательский трекер на своём VPS — дизайн

Статус: **утверждено владельцем 2026-09-11** (решения по входу, регистрации, интеграциям и переезду — ниже, помечены «Решение владельца»). Реализация — `docs/superpowers/plans/2026-09-11-multi-user-hosting.md`.

## Что хотим

1. Трекер живёт в интернете на своём домене, на VPS владельца, по HTTPS.
2. Им пользуются несколько человек. У каждого свои сферы, дни, GTD, рутины, настройки, Telegram-бот, iCloud и Session — и никто не видит чужого.
3. **Регистрация — по почте через Resend** (письмо с подтверждением), **вход — почта + пароль**. Регистрироваться может **любой адрес**.
4. **iCloud Reminders и Session.app — опциональные**, настраиваются каждым пользователем в интерфейсе, как Telegram после плана №1 (из env → в настройки).
5. Все текущие данные владельца переезжают в онлайн-версию **без потерь**, с продуманным переходным периодом (транзитом): без задвоений в Telegram и iCloud, с возможностью откатиться.
6. Разработка — в отдельной ветке, развёртывание — повторяемое, из репозитория.

## Предпосылка

Сначала выполняется и мёржится `docs/superpowers/plans/2026-09-11-distraction-and-telegram-settings.md`: там токен бота и чаты переезжают из env в БД, а YouTube становится «залипанием». Здесь тот же приём повторяется для iCloud и Session.

## Развилка 0. Как вообще получить «несколько пользователей»

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| 0a. Инстанс на человека | Каждому свой docker-compose-стек и поддомен, вход — `basic_auth` в Caddy | Ноль изменений кода | ~400–600 МБ RAM на человека; N стеков обновлять; вход — браузерное окошко |
| **0b. Один инстанс, `userId` в каждой таблице** | Мультиарендность на уровне приложения | Один стек, нормальный вход, десятки пользователей на одном VPS | Переписать доступ к данным во всех сервисах; риск утечки лечится e2e-тестом изоляции |
| 0c. Схема/БД Postgres на пользователя | `search_path` на запрос | Сильная изоляция | Prisma поддерживает плохо, миграции N раз |

**Решение:** **0b**. Вариант 0a не делаем (владелец хочет сразу нормальную многопользовательскую версию).

## Развилка 1. Ветки

- **Решение:** ветка `feat/multi-user` от `master` → по готовности мёрж в `master`. Одна кодовая база, многопользовательская всегда; локально — то же приложение с регистрацией/входом.

## Развилка 2. Изоляция данных

### Какие таблицы получают `userId`

Корневые: `Category`, `Day`, `TaskTemplate`, `Settings`, `GtdItem`, `Routine`, `TelegramChat`.
Дочерние наследуют владельца через родителя: `DayCategoryStatus` (→ Day), `RoutineLog` (→ Routine), `TelegramPost` (→ Day), `DailyTask` (→ Day, легаси).

Уникальности — в пределах пользователя:
- `Category.key` → `@@unique([userId, key])`
- `Day.date` → `@@unique([userId, date])`
- `TelegramChat.chatId` → `@@unique([userId, chatId])`
- `Settings`: синглтон `id = 1` → `id autoincrement` + `userId @unique`.

### Как код гарантирует изоляцию

| Вариант | Оценка |
|---|---|
| **Явный `userId` первым аргументом каждого метода сервиса + `where: { userId }`** (решение) | Явно, грепается, тестируется моком Prisma в стиле репо |
| Prisma Client extension с автоподмешиванием `userId` | Магия, легко пропустить `findUnique`/вложенные записи/`$queryRaw` |
| Postgres Row Level Security | Надёжно, но с Prisma нужен `SET app.user_id` в транзакции на каждый запрос; можно позже вторым рубежом |

Правила:
1. Доступ по id — только `where: { id, userId }`. Чужая запись → **404** (не 403).
2. Ссылки между записями (`DayCategoryStatus.categoryId`, `GtdItem.parentId`, `Routine.categoryId`) проверяются на того же владельца.
3. **e2e-тест изоляции** на реальной БД: два пользователя, B пытается читать/менять/удалять данные A по каждому эндпоинту → 404 / пусто. Без него фича не готова.

## Развилка 3. Вход

### Решение владельца: регистрация через письмо (Resend), вход по паролю

Resend **обязателен**: через него идут письмо подтверждения при регистрации и письмо сброса пароля. Каждый вход после этого — только почта + пароль, без писем.

| Вариант | Почему не основной |
|---|---|
| Магическая ссылка/код на каждый вход | Письмо на каждый вход — лишнее трение; владелец выбрал пароль, почта — только для регистрации и сброса |
| Регистрация без подтверждения почты | Можно занять чужой адрес, а сброс пароля уйдёт владельцу адреса; открытая регистрация без подтверждения — лёгкая цель для ботов |
| OAuth / Telegram Login | Регистрация приложений у провайдеров, не у всех друзей есть аккаунт; можно добавить позже |
| Внешние сервисы (Clerk, Supabase Auth, Auth0) | Лишняя зависимость и данные пользователей у третьей стороны для self-hosted проекта |
| better-auth | Хорошая библиотека, но своя схема таблиц и роутинг, интеграция с Nest через сторонний адаптер. Для «почта+пароль+сессии» своя реализация короче |

**Своя реализация** в модуле `backend/src/auth/` (~300 строк, в стиле репо, покрыта unit- и e2e-тестами).

### Хранение паролей

- **scrypt из `node:crypto`** (`N=2^15, r=8, p=1`, соль 16 байт, ключ 64 байта), формат строки `scrypt$32768$8$1$<salt b64>$<hash b64>` — параметры хранятся в строке, их можно усилить позже без миграции (перехэширование при следующем входе).
- Почему не `Bun.password` (argon2id): бэкенд в проде работает на Bun, но Jest-тесты идут под Node, где `Bun.*` нет. Почему не пакет `argon2`: нативная сборка под Alpine/musl — лишний риск в Docker-образе. scrypt встроен и в Node, и в Bun.
- Проверка — `timingSafeEqual`. Если пользователя нет — всё равно считается scrypt от «пустышки», чтобы по времени ответа нельзя было понять, существует ли адрес.
- Пароль: 8–128 символов, без иных правил состава (NIST 800-63B). Проверку по утёкшим паролям (HIBP) — не делаем.

### Регистрация — решение владельца: любые адреса, подтверждение через Resend

Поток:
1. `/register`: почта + пароль + повтор → `POST /auth/register`. Создаётся **неподтверждённая** запись `PendingSignup` (email, хэш пароля, sha256 токена и 6-значного кода, срок 24 часа) — не `User`. Уходит письмо через Resend: ссылка `https://<домен>/register/confirm?token=…` и код.
2. Пользователь открывает ссылку (страница сама делает `POST /auth/register/confirm {token}` — почтовые сканеры открывают GET-ссылки и сжигали бы токен) **или** вводит код на экране «Проверьте почту» (`{email, code}`, до 5 попыток).
3. Подтверждение → создаются `User` (с тем паролем, что задан на шаге 1), настройки, дефолтные сферы; сразу выдаётся сессия.
4. Ответ на шаге 1 всегда одинаковый («Мы отправили письмо на …»). Если адрес уже зарегистрирован — вместо письма подтверждения туда уходит письмо «Кто-то пытался зарегистрироваться на ваш адрес. Если это вы — войдите или сбросьте пароль». Так регистрация не раскрывает, какие адреса заняты.
5. Повторная регистрация на тот же адрес до подтверждения заменяет прежнюю `PendingSignup` (новый пароль, новый токен). Просроченные записи чистятся при старте и раз в сутки.

Кто может регистрироваться: `SIGNUP_MODE=open` по умолчанию (любой адрес). Переключатели `allowlist` (`ALLOWED_EMAILS`) и `closed` оставлены в env — на случай наплыва ботов. Регистрация, не прошедшая подтверждение, не занимает места в основных таблицах.

### Сброс пароля (через Resend)

- «Забыли пароль?» → `POST /auth/forgot {email}` → письмо со ссылкой `https://<домен>/reset?token=…` (sha256 токена в БД, 30 минут, одноразовый). Ответ одинаковый для существующих и несуществующих адресов.
- `/reset` сама делает `POST /auth/reset {token, password}`; успех закрывает все сессии пользователя и выдаёт новую.
- Аварийный путь на сервере (Resend недоступен, почта потеряна): `bun run reset-password --email x` — пароль вводится интерактивно или `--password-stdin`, никогда аргументом (иначе останется в истории shell).
- Смена пароля в «Аккаунте» требует текущий пароль и закрывает все остальные сессии.

### Письма

Отправка — HTTP API Resend (`POST https://api.resend.com/emails`), без SDK. Три шаблона, по-русски, строковые с `escapeHtml`: подтверждение регистрации, «адрес уже зарегистрирован», сброс пароля. В продакшене бэкенд **не стартует** без `RESEND_API_KEY` и `MAIL_FROM`. Локально без ключа письма печатаются в лог бэкенда (только при `NODE_ENV !== 'production'`). Бесплатный тариф Resend (~100 писем/день) для этого проекта с запасом; rate limit на регистрацию/сброс защищает квоту.

### Сессии

- Таблица `Session` (в БД только sha256 токена), cookie `sid`: `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=30 дней`, продление при активности не чаще раза в сутки.
- Глобальный `SessionGuard`, `@Public()` для `/auth/*` и `/health`. Нет сессии → 401 → фронт уводит на `/login`.
- `POST /auth/logout`, `POST /auth/logout-all`.

### Защита

- Rate limit (`@nestjs/throttler`): `/auth/login` — 5/мин на IP и 10/15 мин на email; `/auth/register` — 3/час на IP и на email; `/auth/register/confirm` — 10/мин на IP; `/auth/forgot` — 3/час на IP и на email. За Caddy — `trust proxy`, иначе все запросы «с одного IP».
- CSRF: `SameSite=Lax` + мутации только с `Content-Type: application/json` + строгий CORS.
- Ошибки входа одинаковые: «Неверная почта или пароль». Регистрация и сброс не раскрывают, занят ли адрес (см. выше).
- Секреты интеграций в БД (токен Telegram-бота, пароль приложения iCloud) — AES-256-GCM ключом `APP_ENCRYPTION_KEY`. Потеря ключа = потеря этих секретов (данные трекера не страдают, секреты вводятся заново). Ключ хранить в менеджере паролей.

## Развилка 4. Интеграции: из env — в настройки пользователя

Принцип тот же, что в плане №1 для Telegram: у каждого пользователя свои учётные данные в БД, вкладка в настройках, проверка при сохранении, секрет никогда не возвращается API целиком. **Env-фоллбэков в многопользовательском режиме нет** — иначе чужие действия уходили бы в iCloud/Telegram владельца.

| Интеграция | Сейчас | Станет |
|---|---|---|
| Telegram | БД (после плана №1) + env-фоллбэк | БД, у каждого свой. Env-фоллбэк удалён |
| **iCloud Reminders** | `ICLOUD_APPLE_ID`, `ICLOUD_APP_PASSWORD`, `ICLOUD_REMINDERS_LIST_NAME` | Вкладка «iCloud»: Apple ID, пароль приложения (зашифрован), имя списка (по умолчанию «GTD»). Опционально: пусто — синк молча выключен |
| **Session.app → помидорки** | `SESSION_CALENDAR_NAME`, `SESSION_MIN_MINUTES`, `TZ` | Вкладка «Session»: имя календаря, минимальная длина сессии (по умолчанию 20). Использует учётку из вкладки «iCloud» и **часовой пояс пользователя** вместо `TZ`. Опционально |
| Obsidian-экспорт | Папка на хосте | На VPS выключен (нет смысла писать в папку сервера). Позже — «скачать ZIP» |
| Браузерные уведомления | Нужен HTTPS | На домене с Let's Encrypt работают |

Технические последствия:
- `CalDavClient` сейчас держит **один** кэшированный клиент на процесс по env-учётке. Станет кэш `Map<userId, { fingerprint, client }>`; смена/удаление учётки сбрасывает запись; неудачный логин не кэшируется (сохраняем текущее правило из git-истории).
- `ICloudService`/`SessionService` принимают `userId`, берут учётку из `Settings` пользователя.
- Стартовый синк (`main.ts` → `syncAllOnStartup`) идёт по всем пользователям с настроенным iCloud, последовательно; плюс кнопка «Синхронизировать все напоминания» во вкладке «iCloud».
- Сохранение учётки iCloud проверяется реальным логином в CalDAV и поиском списка; Session — поиском календаря. Ошибка → понятный текст, ничего не сохраняется.
- UID напоминаний детерминированный (`gtd-rem-<id>`) и **зависит только от id GTD-элемента** — это важно для переезда: id сохраняются дампом, поэтому серверная версия обновит те же напоминания, а не создаст дубли.
- Флаги `icloudEnabled`, `sessionSyncEnabled` в `GET /settings` становятся per-user; фронт по ним прячет кнопки.
- Локальный dev-стек после переезда **не должен** иметь рабочих учёток iCloud/Telegram владельца (см. «Транзит»).

## Развилка 5. Время и «сегодня»

`todayDate()` на бэкенде сейчас берёт `TZ` контейнера (`stats.service.ts` ×3, `days.service.ts` getHistory, `routines.service.ts` ×2, `obsidian.service.ts`), а Session — `process.env.TZ`. **Решение:** `User.timezone` (IANA), при регистрации фронт присылает `Intl.DateTimeFormat().resolvedOptions().timeZone`, меняется в «Аккаунте»; хелпер `todayFor(timezone)`; Session считает окна дня в поясе пользователя. Контейнер — `TZ=UTC`.

## Развилка 6. Хостинг

### VPS

Ubuntu 24.04, **2 vCPU / 4 ГБ** (сборка Next.js ~1–1,5 ГБ; на 2 ГБ — со swap). Регион — где доступны `api.telegram.org`, `caldav.icloud.com`, `api.resend.com`: проверить `curl -sI` с сервера до покупки на долгий срок.

### Как выкатывать

| Вариант | Когда |
|---|---|
| **A. `git pull` + `docker compose -f docker-compose.prod.yml up -d --build` на VPS** (решение) | Старт |
| B. GitHub Actions → образы в GHCR → `docker compose pull` на VPS | Когда сборка на сервере надоест или VPS маленький |
| C. Coolify / Dokploy | Если захочется веб-панель с авто-SSL и бэкапами |

### Схема

```
интернет ──443/80──▶ caddy (Let's Encrypt) ──┬─ /api/* ─▶ backend:3001 ─▶ postgres:5432
                                              └─ /*     ─▶ frontend:3000
```

- Наружу только **80/443**. **Ловушка:** Docker публикует порты в обход UFW, а текущий `docker-compose.yml` публикует Postgres на `5434` с паролем `tracker`. Поэтому отдельный `docker-compose.prod.yml` без `ports:` у `postgres`/`backend`/`frontend` и с сильным паролем БД.
- Один origin для фронта и API (`/api` через Caddy) → cookie первого лица; `NEXT_PUBLIC_API_URL=/api`.
- Тома: `pgdata`, `caddy_data` (сертификаты — без тома лимиты Let's Encrypt), `caddy_config`.
- Из `CMD` бэкенда убрать `prisma db seed` (глобальных сфер больше нет — дефолтные создаются при регистрации).
- Ротация логов docker (`max-size: 10m`).

### Бэкапы

Ночной `pg_dump -Fc` по cron → `/var/backups/tracker`, хранение 14 дней + копия вне сервера (`rclone` в S3-совместимое хранилище). Дамп перед каждым деплоем. Раз в месяц — пробное восстановление.

### Защита сервера

SSH по ключам, без пароля и root-входа, пользователь `deploy`, `ufw` (22/80/443), `fail2ban`, `unattended-upgrades`, внешний пинг `https://домен/api/health`.

### Домен и почта (руками владельца)

1. Купить домен, A/AAAA-запись на IP VPS.
2. **Resend — обязательно** (регистрация и сброс пароля): добавить домен (лучше поддомен `mail.домен`), DNS-записи DKIM/SPF/MX + `_dmarc` (`v=DMARC1; p=none;`), дождаться Verified, ключ «Sending access», `MAIL_FROM="Трекер <noreply@mail.домен>"`. Без DKIM/SPF письма подтверждения уходят в спам — проверить на Gmail и на почте друга до того, как звать людей.

## Развилка 7. Переезд данных владельца и транзит

### Способ

| Вариант | Оценка |
|---|---|
| **Дамп локальной БД → восстановление на VPS → миграции приложения превращают однопользовательские данные в аккаунт владельца** (решение) | Все id, история, GTD, рутины, отметки Telegram-публикаций переезжают как есть; кастомного экспорта нет |
| JSON-экспорт/импорт | Легко забыть сущность; id поменялись бы → iCloud-напоминания задвоились бы (UID от id). Отвергнуто для переезда |

Миграция `multi_user` при наличии данных создаёт пользователя `owner@localhost.invalid` без пароля и отдаёт ему все корневые записи. Скрипт `set-owner` ставит настоящую почту и пароль.

### Транзит — что может пойти не так между «работаю локально» и «работаю онлайн»

| Риск | Что делаем |
|---|---|
| Данные расходятся: что-то внесено локально после дампа | **Окно заморозки**: финальный дамп снимается только после `docker compose stop backend frontend` локально. До этого — сколько угодно репетиций на копиях |
| Неконсистентный дамп (запись посреди дампа) | Бэкенд остановлен → писать некому. `pg_dump` и так снимает снапшот транзакции, но остановка убирает и «полузаписанные» пользовательские сценарии |
| **Двойные посты в Telegram** (локальный и серверный инстансы оба закрывают день) | Отметки публикаций (`TelegramPost`, легаси-колонки `Day`) едут в дампе → сервер знает, что уже отправлено. Локальный инстанс после переезда запускается только **без** токена бота: скрипт транзита очищает `Settings.telegramBotToken` в локальной БД после финального дампа |
| **Конфликт в iCloud** (оба инстанса пишут/удаляют одни и те же напоминания) | Локально iCloud-учётка живёт в `.env` → после финального дампа **убрать `ICLOUD_*` и `SESSION_*` из локального `.env`**. На сервере учётка вводится во вкладке «iCloud» только после этого; кнопка «Синхронизировать все» догоняет состояние. Дублей нет — UID от id, id сохранены |
| Секреты в дампе (токен бота открытым текстом — так он хранится после плана №1) | Передача только `scp` (SSH-шифрование), `chmod 600`, файл на VPS удаляется сразу после восстановления; на сервере токен шифруется при первом старте. Дамп не кладётся ни в git, ни в облачные папки |
| Разные `APP_ENCRYPTION_KEY` локально и на сервере | Финальный дамп снимается с **текущей однопользовательской** версии (секреты ещё не зашифрованы) — ключ сервера используется впервые при старте. Если локально уже крутилась новая версия с шифрованием — на сервере тот же ключ |
| Часовой пояс и даты | `Day.date` — `@db.Date`, от пояса не зависит; владельцу `set-owner --timezone Europe/Moscow`, «сегодня» совпадёт с локальным |
| Помидорки Session пересчитываются по-другому | Session на сервере читает тот же календарь, окна дня — в поясе пользователя (= прежний `TZ` владельца). Перед переездом проверить, что `TZ` в локальном `.env` = выбранный `--timezone` |
| Миграция упала на сервере посреди применения | Прод-БД пустая до восстановления → повторить: пересоздать БД, восстановить дамп заново. Локальная БД не тронута |
| Онлайн-версия оказалась сломанной в первые дни | **Откат**: локальная БД не изменялась → вернуть `.env`, `docker compose start` — работаем локально. Если онлайн уже накопились новые данные — дамп с сервера → восстановить локально в стек ветки `feat/multi-user` (та же схема) |
| Потеря связи/таймаут при `scp` | Сверять контрольную сумму: `shasum -a 256` локально и на сервере |

### Проверка «без потерь»

Скрипт `deploy/verify-migration.sql` считает строки и контрольные суммы по ключевым таблицам (`Day`, `DayCategoryStatus`, `Category`, `GtdItem`, `Routine`, `RoutineLog`, `TaskTemplate`, `TelegramChat`, `TelegramPost`) — запускается на локальной БД до дампа и на сервере после миграций; числа должны совпасть (серверная версия — плюс `userId`, суммы считаются по полям, которые были до переезда).

## Что меняется в интерфейсе

- `/login`: почта + пароль, ссылки «Регистрация» и «Забыли пароль?». `/register`: почта, пароль, повтор → экран «Проверьте почту» с полем кода и «Отправить ещё раз». `/register/confirm`: принимает токен из письма. `/forgot`, `/reset`: сброс пароля.
- Настройки → новые вкладки «Аккаунт» (почта, часовой пояс, смена пароля, выйти, выйти везде), «iCloud», «Session».
- `lib/api.ts`: `credentials: 'include'`; 401 → `/login`.
- `resolveApiUrl()`: если `NEXT_PUBLIC_API_URL` начинается с `/` — путь на своём origin.

## Локальная разработка

- `docker compose up` как раньше; регистрация открыта; без `RESEND_API_KEY` письма (ссылка и код подтверждения, сброс) печатаются в `docker compose logs backend`.
- `COOKIE_SECURE=false` локально (Safari не ставит `Secure`-cookie на `http://localhost`). `localhost:4887` и `localhost:3001` — один «site», `SameSite=Lax` cookie ходит; во фронте `credentials: 'include'`, в CORS `credentials: true`.

## Вне скоупа

Роли/админка, общие между пользователями данные, мобильное приложение/PWA, платежи, горизонтальное масштабирование.
