# Рутины с недельной нормой — дизайн

Дата: 2026-08-12

## Мотивация

Пользователь развёл две сущности, которые сейчас слиплись в трекере:

- **«Позаниматься в качалке»** — рутина, выполняется 3 раза в неделю, у неё нет конца.
- **«Сходить в качалку»** — разовое действие (оформить абонемент, забрать вещи), законная GTD-задача с завершением.

Рутины частично покрыты дневными категориями (`Category`), но у категории нет понятия нормы: галочка бинарная и ежедневная, поэтому один поход в неделю выглядит ровно так же, как три. Замер на 2026-08-12 (сфера «Спорт», 32 дня трекинга с 09.07):

| Неделя | Дней со спортом |
|---|---|
| 10.08 | 1 |
| 03.08 | 1 |
| 20.07 | 2 |
| 13.07 | 1 |

5 дней за месяц при цели 3 в неделю, и система об этом молчит — она не знает, что цель существует.

Вторая проблема — куда такие вещи записывать. Не имея места для рутины, пользователь заводит её как обычную GTD-задачу («Сходить в качалку» в бэклоге), она выполняется, исчезает, а на следующей неделе записывается заново. Это шум в бэклоге и потеря истории.

## Решения (зафиксировано на брейншторме 2026-08-12)

- Рутина — это **норма N раз в неделю**, любые дни. Расписание по конкретным дням недели не делаем.
- Рутины живут на **отдельной вкладке**, третьей рядом с «Главный» и «GTD». Отметка выполнения — **только там**, главный экран дня не трогаем.
- Рутина может быть **привязана к сфере** (`categoryId`, необязательно). Отметка рутины закрывает галочку сферы за этот день — двойного ввода нет.
- Недобор нормы разбирается **в воскресном обзоре**: подтвердить норму, снизить или удалить рутину.
- Неделя — **пн–вс**, как в уже существующей статистике.

## Модель данных

```prisma
model Routine {
  id         Int          @id @default(autoincrement())
  title      String
  weeklyGoal Int          @default(3)
  categoryId Int?
  category   Category?    @relation(fields: [categoryId], references: [id], onDelete: SetNull)
  archived   Boolean      @default(false)
  order      Int          @default(0)
  logs       RoutineLog[]
  createdAt  DateTime     @default(now())
}

model RoutineLog {
  id        Int      @id @default(autoincrement())
  routineId Int
  routine   Routine  @relation(fields: [routineId], references: [id], onDelete: Cascade)
  date      DateTime @db.Date

  @@unique([routineId, date])
}
```

Уникальность `(routineId, date)` — одна отметка в день: «качалка 3/нед» это три **разных дня**, а не три подхода. Повторный запрос на ту же дату идемпотентен.

Норма живёт на рутине, факт — в логах. Поэтому снижение нормы задним числом не переписывает историю: прошедшие недели по-прежнему считаются от логов, а сравнение с нормой всегда идёт с текущим значением. Это осознанное упрощение — версионировать норму не нужно, недельный отчёт нужен как сигнал, а не как юридический документ.

`archived` вместо жёсткого удаления: удалённая рутина унесла бы логи каскадом, а история выполнения — самое ценное, что здесь есть. `DELETE /routines/:id` архивирует.

Категория получает обратную связь `routines Routine[]`.

## Границы недели

`StatsService.mondayOf()` (`backend/src/stats/stats.service.ts:195`) уже реализует неделю пн–вс, но приватным методом. Он переезжает в `backend/src/common/date.util.ts` как экспортируемый `mondayOf(date: Date): Date`, а `StatsService` начинает импортировать его оттуда. Иначе появится вторая реализация границы недели, и однажды они разойдутся — вкладка рутин и недельная сводка начнут показывать разные недели.

Рефакторинг сопровождается тестом на `mondayOf` в `common` (воскресенье → предыдущий понедельник, понедельник → сам себя) и прогоном существующих тестов `stats.service.spec.ts` без изменений.

## Backend — `backend/src/routines/`

Модуль по образцу остальных фич: `routines.controller.ts`, `routines.service.ts`, `routines.module.ts`, `dto/`, `routines.service.spec.ts` с замоканным `PrismaService` (обычный `new RoutinesService(mockPrisma)`, без `@nestjs/testing`).

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/routines?week=YYYY-MM-DD` | живые рутины с прогрессом за неделю, содержащую эту дату; без параметра — текущая неделя по `todayDate()` |
| `POST` | `/routines` | `{ title, weeklyGoal, categoryId? }` |
| `PATCH` | `/routines/:id` | `{ title?, weeklyGoal?, categoryId?, archived? }` |
| `DELETE` | `/routines/:id` | архивирует (`archived = true`), логи сохраняются |
| `POST` | `/routines/:id/log` | `{ date }` — идемпотентно; побочный эффект по сфере (ниже) |
| `DELETE` | `/routines/:id/log/:date` | снимает отметку |
| `GET` | `/routines/history?weeks=8` | по неделям: `{ weekStart, items: [{ routineId, done, weeklyGoal }] }` |

Форма элемента в `GET /routines`:

```ts
interface RoutineView {
  id: number;
  title: string;
  weeklyGoal: number;
  categoryId: number | null;
  done: number;        // отметок на этой неделе
  days: string[];      // YYYY-MM-DD отмеченных дней, по возрастанию
  order: number;
}
```

`weekStart`/`weekEnd` возвращаются рядом со списком, чтобы фронт не пересчитывал границы самостоятельно.

Валидация `weeklyGoal`: целое от 1 до 7. Больше семи при одной отметке в день недостижимо, и это должна ловить валидация, а не пользователь.

## Связь со сферой

При `POST /routines/:id/log` для рутины с непустым `categoryId` сервис проставляет `DayCategoryStatus.done = true` для этой категории за эту дату (создавая `Day`, если его ещё нет — как это делают существующие эндпоинты дня).

`DELETE .../log/:date` галочку сферы **не снимает**. Асимметрия намеренная: сферу «Спорт» можно закрыть и по другой причине (пробежка вместо качалки), и снятие отметки рутины не даёт системе права стирать этот факт. Правило простое и объяснимое; попытка «умно» отслеживать причину закрытия сферы породила бы состояние, за которым невозможно уследить.

Существующие стрик и статистика при этом продолжают работать без изменений — они читают `DayCategoryStatus` и не знают о рутинах.

## Фронтенд — вкладка «Рутины»

`Dashboard.TABS` получает третий элемент `{ key: 'routines', label: 'Рутины' }`. В подписи таба — счётчик рутин, у которых норма на текущей неделе ещё не закрыта (`Рутины 2`): отметка живёт только здесь, и без напоминания на вкладку легко не зайти.

Новый `'use client'`-компонент `RoutinesScreen.tsx` со своим фетчем на маунте — по образцу `CategoryBars`/`TaskTemplatesTab`, а не через состояние `Dashboard`.

Текущая неделя, по строке на рутину:

```
Позаниматься в качалке        ●●○○○○○   2/3   [+ отметить сегодня]
Растяжка                      ●●●●●●●   7/3   [✓ отмечено]
```

- Точки — дни недели пн–вс; заполненные соответствуют `days`.
- Перевыполнение (`7/3`) показывается как есть, не считается ошибкой.
- Кнопка отмечает **сегодняшний** день (`todayLocal()`); повторный клик снимает отметку.
- Отметить задним числом можно кликом по точке нужного дня — прошедшие дни кликабельны, будущие нет.

Ниже — история за 8 недель (`GET /routines/history`) в стиле существующих хитмапов: строка на рутину, колонка на неделю, цвет — доля выполнения от нормы (`heatmap.ts`, отдельная функция бакетирования по доле, не по абсолютному числу).

Настройка рутин (создать / переименовать / изменить норму / привязать сферу / архивировать) — там же на вкладке, в свёрнутом блоке, по образцу управления категориями.

CSS — модуль `RoutinesScreen.module.css` на существующих токенах из `globals.css`, без новых цветов.

## Воскресный обзор

В `WeeklyReview` добавляется шаг **«Рутины»** — рядом с шагом протухших задач из спеки `2026-08-12-gtd-bucket-semantics-design.md`. Показываются только рутины, недобравшие норму на завершающейся неделе:

> «Позаниматься в качалке» — 1 из 3 на этой неделе. Норма реальная?
> `Оставить` · `Снизить до 2` · `Удалить рутину`

- `Оставить` → ничего не меняет, шаг по этой рутине закрыт
- `Снизить до N-1` → `PATCH { weeklyGoal: weeklyGoal - 1 }`; при норме 1 вариант не показывается
- `Удалить рутину` → `DELETE` (архивация)

Тот же принцип, что и с откладываемыми задачами: система не констатирует провал, а раз в неделю требует либо подтвердить обязательство, либо честно его понизить. Норма 3, выполняемая на 1, — это не мотивация, а фоновое чувство вины.

Обзор открывается в воскресенье, то есть в последний день недели: он спрашивает про **текущую**, ещё не закрытую неделю. Отметка, сделанная в воскресенье после обзора, просто улучшит результат недели — повторно спрашивать не нужно.

## Тесты (TDD)

Бэкенд (`backend/src/routines/routines.service.spec.ts`):
- `GET /routines` считает `done` только по дням внутри недели, соседние недели не подмешиваются.
- Воскресная дата в `?week=` попадает в неделю, начинающуюся предыдущим понедельником.
- `POST /log` дважды на одну дату не создаёт вторую запись и не падает.
- `POST /log` рутины с `categoryId` проставляет `DayCategoryStatus.done`; без `categoryId` — не трогает.
- `DELETE /log` не снимает галочку сферы.
- `DELETE /routines/:id` архивирует, а не удаляет; логи на месте; архивная рутина не приходит в `GET /routines`.
- `weeklyGoal` вне диапазона 1–7 отклоняется.

`backend/src/common/date.util.spec.ts`:
- `mondayOf` — понедельник возвращает себя, воскресенье возвращает предыдущий понедельник, середина недели корректна.

Фронтенд (`frontend/lib/routines.spec.ts`):
- бакетирование доли выполнения для хитмапа (0, недобор, ровно норма, перевыполнение);
- счётчик незакрытых рутин для подписи таба.

## Не входит в объём

- Расписание по конкретным дням недели (пн/ср/пт) — решено делать только норму.
- Несколько отметок за один день.
- Версионирование нормы и пересчёт истории при её изменении.
- Отметка рутин с главного экрана дня.
- Напоминания/уведомления по рутинам.
- Перенос существующих категорий в рутины — сферы остаются как есть.
- Автоматическое распознавание рутины среди GTD-задач («сходить в качалку» → рутина) — перенос делается руками.
