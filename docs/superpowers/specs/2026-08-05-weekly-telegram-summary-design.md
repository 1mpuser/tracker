# Недельная сводка в Telegram с графиком — дизайн

## Мотивация

Дневная сводка уже уходит в канал при закрытии дня (`docs/superpowers/specs/2026-08-01-telegram-day-summary-design.md`), и в ленте копится история по дням. Чего в ней нет — взгляда на неделю целиком: сколько помидорок вышло суммарно, какой день вытянул, какие сферы просели, держится ли средняя оценка.

Задача: при закрытии воскресенья публиковать в тот же канал одну недельную сводку — картинку с графиком помидорок по дням и текст с итогами.

## Решения (зафиксировано на брейншторме)

- **Триггер — закрытие воскресного дня.** Никакого планировщика в бэкенде нет и не заводим: закрытие дня уже событие в коде, а воскресное GTD-ревью в этом проекте тоже сделано без cron. Цена решения: не закрыл воскресенье — сводки за эту неделю не будет. Это принято сознательно.
- **График рисует фронтенд.** Бэкенд — Bun-процесс в alpine-контейнере: ни браузера, ни canvas, ни шрифтов. Recharts, которым нарисованы графики в интерфейсе, работает только в DOM. Поскольку закрытие дня — это клик в браузере, картинку рисует та же страница теми же компонентами и отдаёт готовый PNG бэкенду. Отвергнут внешний сервис (QuickChart): он тянет данные на чужой сервер и даёт графики чужого вида. Отвергнут собственный энкодер PNG в бэкенде: без шрифтов подписи осей рисовать нечем, а результат всё равно не совпал бы с интерфейсом.
- **Текст сводки собирает бэкенд из базы.** Клиент присылает только пиксели. Иначе клиент мог бы прислать любые числа, и пост разошёлся бы с тем, что в базе.
- **Один пост на неделю.** Идемпотентность — атомарный захват нового поля `Day.weeklyTelegramMessageId` на строке воскресенья, тем же приёмом `updateMany` с условием в `where`, что уже защищает дневную сводку (`days.service.ts:135-146`).
- **Картинка не обязательна.** Если фронт не смог её снять, сводка уходит текстом. Терять недельный итог из-за сбоя рендера нельзя.
- **Неделя — понедельник по воскресенье** того воскресенья, которое закрыли.

## Поток

1. Пользователь закрывает воскресенье — на главном экране или в модалке прошедшего дня. Обе точки зовут один и тот же `updateDay(date, { eveningClosed: true })`.
2. Бэкенд, как и сегодня, публикует дневную сводку.
3. Фронт видит, что закрытая дата — воскресенье, и что день только что перешёл в закрытое состояние. Тянет `GET /stats/week?end=<дата>`, рендерит скрытый график, снимает с него PNG.
4. Фронт зовёт `POST /days/:date/weekly-summary` с этим PNG в теле.
5. Бэкенд захватывает `weeklyTelegramMessageId`, собирает текст из базы и публикует: `sendPhoto` с подписью, либо `sendMessage`, если картинки нет.

Шаг 3 не блокирует интерфейс: пользователь уже увидел закрытый день, картинка снимается и уходит фоном.

## Модель данных

Одна миграция, одно nullable-поле:

```prisma
model Day {
  // ...
  telegramMessageId       Int?
  weeklyTelegramMessageId Int?   // новое: пост недельной сводки этой (воскресной) даты
}
```

Поле заполняется только у воскресений. У остальных дат остаётся `null` навсегда — это нормально и ничего не стоит.

## API

### `GET /stats/week?end=YYYY-MM-DD`

Отдаёт агрегат недели, заканчивающейся указанной датой. Используется фронтом для графика; тем же методом сервиса бэкенд собирает текст сводки, поэтому цифры в подписи и на картинке не могут разойтись.

```ts
interface WeekStats {
  weekStart: string;              // YYYY-MM-DD, понедельник
  weekEnd: string;                // YYYY-MM-DD, воскресенье
  days: {
    date: string;
    weekday: string;              // 'Пн'…'Вс'
    pomodoros: number;
    rating: number | null;
    closed: boolean;
  }[];
  totalPomodoros: number;
  avgPomodoros: number;           // с одним знаком после запятой
  bestDay: { date: string; weekday: string; pomodoros: number } | null;  // null, если помидорок за неделю ноль
  avgRating: number | null;       // среднее только по дням с оценкой; null, если оценок нет
  ratedDays: number;
  categories: { label: string; doneCount: number }[];  // из 7
  youtubeAvgMinutes: number;
  youtubeBudget: number;
}
```

Правила агрегации:
- Дни без строки в БД считаются нулями, а не пропускаются — неделя всегда ровно 7 точек, иначе график поедет.
- `avgPomodoros` — сумма, делённая на 7, а не на число закрытых дней.
- `avgRating` — только по дням, где оценка проставлена. Незакрытый день не тянет среднее вниз.
- `bestDay` при ничьей — самый ранний из равных.

### `POST /days/:date/weekly-summary`

```jsonc
{ "chartPng": "<base64 без префикса data:>" }   // поле необязательно
```

Ответы:
- `200 { "posted": true, "withChart": true|false }` — опубликовано.
- `200 { "posted": false, "reason": "already-posted" }` — за эту неделю уже публиковали. Не ошибка: фронт может позвать повторно после переоткрытия дня.
- `400` — дата не воскресенье, или `chartPng` не похож на base64 PNG.
- `409` — Telegram не настроен (`TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` пусты).
- `502` — Telegram не принял пост. Захват освобождается, следующая попытка возможна.

Картинка передаётся base64-строкой в обычном JSON: так не нужен `multer` и никаких новых зависимостей. В `main.ts` поднимается лимит тела запроса до 2 МБ — дефолтные 100 КБ для PNG малы. Конкретный способ (штатный `useBodyParser` на express-приложении либо отключение встроенного парсера и явный `express.json({ limit })`) выбирается при реализации, важен результат: PNG на пару сотен килобайт проходит, а лимит не снят совсем.

В Telegram картинка уходит как файл: base64 разворачивается в `Buffer`, кладётся в `FormData` и отправляется на `sendPhoto`. Ни `FormData`, ни `Blob` ставить не нужно — оба глобальны в Bun.

## Формат поста

`parse_mode: HTML`, экранирование через существующий `escapeHtml` из `telegram.helpers.ts`.

```
📊 Неделя 29 июля — 4 августа 2026

🍅 Помидорок: 34 (в среднем 4.9/день)
🔥 Лучший день: среда — 8
⭐ Средняя оценка: 7.4/10 (по 6 дням)

Сферы за неделю
✅ Спорт 5/7
⚠️ Финансы 3/7
❌ Личная жизнь / семья 1/7

📺 YouTube: 42 мин/день при бюджете 60
```

Значки сфер по доле выполненных дней: `✅` от 5 из 7, `⚠️` от 2 до 4, `❌` при 0–1.

Строка оценки опускается целиком, если за неделю не выставлено ни одной. Строка лучшего дня опускается, если помидорок за неделю ноль.

**Лимит подписи.** У Telegram подпись к фото ограничена 1024 символами, а сфер со временем может стать больше. Если текст не влезает, публикуются два сообщения: сначала фото без подписи, затем текст. Проверка идёт по длине готовой строки, а не по числу сфер.

## График

Новый компонент `frontend/components/WeeklyChart.tsx` на Recharts (библиотека уже стоит).

- Столбчатая диаграмма: 7 столбиков помидорок, подписи `Пн`…`Вс`.
- Горизонтальная пунктирная линия минимума на `POMODORO_MIN` (4) — та же константа, что и в панели помидорок.
- Лучший день недели красится в `#ff6f5c`, остальные в `#e0574e`, фон `#1a1d24`, подписи `#888d98`.

Две вещи, без которых экспорт ломается, и потому они часть дизайна, а не деталь реализации:

1. **Анимация выключена** (`isAnimationActive={false}`). Иначе снимок ловит промежуточный кадр и в канал уходит график с недорисованными столбиками.
2. **Цвета заданы литеральными hex, а не `var(--pom)`.** При сериализации SVG в отрыве от документа CSS-переменные не разрешаются, и график уезжает чёрным.

Компонент рендерится вне видимой области (`position: absolute; left: -10000px`) с явными размерами 800×400, а не через `ResponsiveContainer`: у контейнера вне потока нулевая ширина, и график не нарисуется вовсе.

## Снятие PNG

`frontend/lib/chart-export.ts`, одна функция:

```ts
export async function svgToPngBase64(svg: SVGSVGElement, scale = 2): Promise<string>;
```

Шаги: `XMLSerializer` → `Blob` типа `image/svg+xml` → `URL.createObjectURL` → `Image` → отрисовка на `canvas` размером `800*scale × 400*scale` → `toDataURL('image/png')` → отрезать префикс `data:image/png;base64,`.

Фон холста заливается `#1a1d24` перед отрисовкой: SVG прозрачен, а в тёмной теме Telegram прозрачный PNG выглядит как дыра.

`URL.revokeObjectURL` вызывается в `finally` — иначе каждая сводка подтекает блобом.

Функция ничего не знает про недели и помидорки: на вход SVG, на выход base64. Это делает её проверяемой отдельно и переиспользуемой, если когда-нибудь понадобится выгружать другой график.

## Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Не воскресенье | Фронт не делает ничего; эндпоинт при прямом вызове отвечает `400` |
| За эту неделю уже публиковали | `{ posted: false, reason: 'already-posted' }`, ничего не отправляется |
| `canvas` не отдал картинку | Фронт зовёт эндпоинт без `chartPng` — уходит текстовый пост |
| Фронт вообще не дошёл до вызова (закрыли день курлом) | Сводки нет; следующее закрытие этого воскресенья опубликует |
| Telegram не настроен | `409`, в лог ничего тревожного |
| Telegram вернул ошибку | `logger.warn` с вырезанным токеном, захват сбрасывается в `null`, `502` наружу |
| Ошибка на любом шаге | Закрытие дня не ломается — оно к этому моменту уже завершилось отдельным запросом |

Токен не должен попадать в лог — используется тот же приём вырезания секрета, что в `telegram.service.ts:40`.

## Тестирование

**`weekly.helpers.spec.ts`** (чистые функции): границы недели для воскресенья и для даты в середине недели; значок сферы на границах 5/7, 4/7, 1/7; текст без строки оценки, когда оценок нет; текст без лучшего дня при нуле помидорок; текст длиннее 1024 символов распознаётся как не влезающий в подпись; экранирование `<` в названии сферы.

**`stats.service.spec.ts`** (дополняется): неделя без единой строки в БД даёт 7 нулевых точек; среднее по помидоркам делится на 7; `avgRating` считает только дни с оценкой; `bestDay` при ничьей — самый ранний; `bestDay` равен `null` при нуле помидорок.

**`days.service.spec.ts`** (дополняется): повторный вызов за ту же неделю не шлёт ничего; при ошибке отправки поле возвращается в `null`.

**`telegram.service.spec.ts`** (дополняется): с картинкой уходит `sendPhoto`, без — `sendMessage`; токен не попадает в текст лога.

**`frontend/lib/weekly.spec.ts`**: `isSunday` для воскресенья, понедельника и субботы; сборка серии сохраняет порядок Пн→Вс и подставляет нули.

Компонентных тестов не будет: `@testing-library/react` в проекте нет, а `jest.config.js` матчит только `.spec.ts`. `chart-export.ts` тоже не покрывается юнит-тестом — он целиком состоит из вызовов браузерных API (`XMLSerializer`, `canvas`, `Image`), мок которых проверял бы мок. Его проверяет живой прогон, см. ниже.

## Живая проверка

Автотесты здесь не доказывают главного — что в канал приходит красивая картинка. Поэтому реализация не считается законченной, пока не выполнено:

1. Через браузер закрыть воскресенье (например 2 августа 2026) в модалке прошедшего дня.
2. Убедиться, что в канал пришли фото и текст, а не текст в одиночку.
3. Посмотреть на картинку глазами: столбики дорисованы полностью, цвета не чёрно-белые, фон не прозрачный, подписи дней читаются.

Пункт 3 — единственная проверка, ловящая обе ошибки экспорта (анимация и CSS-переменные), и её нельзя заменить ассертом.

## Что не входит

- Планировщик, шлющий сводку без участия пользователя.
- Сводки за другие периоды (месяц, год).
- Графики по сферам, оценкам и YouTube — в первой версии только помидорки.
- Редактирование уже опубликованного поста.
- Отправка сводки при закрытии дня не из браузера.
