# GTD — ядро (Этап A): захват, воронка обработки, корзины — дизайн

## Мотивация

У задач в трекере одна проблема, видимая прямо в данных: на 2026-07-23 из 22 незакрытых `DailyTask` **14 — перенесённые** (64%). Одни и те же пункты («Составить план бота», «Расписать план по боту system design», «Посмотреть SaaS у Назарова») тащатся изо дня в день и не делаются. «Задачи на сегодня» служат одновременно и хранилищем, и списком на день — отсюда «беговая дорожка переносов».

GTD (Getting Things Done, Д. Аллен) разделяет это на два слоя:

- **Слой хранения («мозг»)** — где живёт всё между «поймал мысль» и «делаю»: Корзина, Бэклог, Календарь, Проекты, Ожидание, Когда-нибудь, Заметки.
- **Слой исполнения** — только то, на что подписался на сегодня (нынешний Главный экран).

Этот спек — **Этап A: ядро GTD** как отдельный экран (слой хранения) с полной воронкой обработки. **Моста к дневным задачам здесь ещё нет** — он Этап B. Приоритеты/дедлайны, воскресный Weekly Review-крон, экспорт в Obsidian — Этап C. См. «Дорожная карта» ниже.

## Дорожная карта (контекст, не объём этого спека)

- **Этап A (этот спек):** сущность `GtdItem`, экран GTD, захват в Корзину, воронка обработки, все корзины-состояния, рекурсивные проекты, Done/Архив.
- **Этап B:** мост «взять в сегодня» — Бэклог/Календарь ↔ дневное исполнение; поглощение нынешней вкладки «Задачи».
- **Этап C:** воскресный крон Weekly Review, приоритет/дедлайн/оценка (опционально), экспорт Заметок в Obsidian.

## Решения (зафиксировано на брейншторме)

- **Одна сущность `GtdItem`**, мигрирующая по статусам-корзинам. Не отдельная таблица на каждую корзину.
- **Корзины-статусы:** `inbox` (Корзина), `backlog` (Бэклог), `calendar` (Календарь), `someday` (Когда-нибудь), `waiting` (Ожидание), `project` (Проект), `reference` (Заметки), `done` (Done), `archived` (Мусор — мягкий архив, видно).
- **Правило 5 минут** (не каноничные 2): одношаговое действие, выполнимое за 5 мин, делается сразу → `done`.
- **Мусор = архивирование** (`archived`), не жёсткое удаление; архив просматриваем.
- **Календарь — отдельный трек:** пункт с датой (`scheduledDate`) обходит развилки «одношаговая?/за 5 мин?».
- **Проекты рекурсивны:** под-задача/«первый шаг» проекта — это тоже `GtdItem` (с `parentId` на проект), падает в Корзину и проходит воронку заново.
- **Разбор Корзины — лёгкий инлайн-процессор** (не тяжёлый модальный мастер): у пункта показываются кнопки-развилки, 1–2 тапа — и пункт улетает в корзину.
- **Отдельный экран/вкладка GTD.** `DailyTask`, панель «Задачи на сегодня», сферы/YouTube/помидорки и нынешняя вкладка «Задачи» (обзор `DailyTask`) в Этапе A **не трогаются** — GTD добавляется рядом. Слияние — Этап B.
- Приоритет/дедлайн/оценку в Этап A **не вводим** (второстепенно; поля доклеим позже).

## Модель данных

Новая таблица, ничего существующего не меняется. Prisma:

```prisma
enum GtdStatus {
  inbox
  backlog
  calendar
  someday
  waiting
  project
  reference
  done
  archived
}

model GtdItem {
  id            Int       @id @default(autoincrement())
  title         String
  notes         String?
  status        GtdStatus @default(inbox)
  parentId      Int?
  parent        GtdItem?  @relation("ProjectChildren", fields: [parentId], references: [id], onDelete: SetNull)
  children      GtdItem[] @relation("ProjectChildren")
  scheduledDate DateTime? @db.Date          // только для calendar
  waitingFor    String?                     // только для waiting (кому делегировано)
  order         Int       @default(0)
  createdAt     DateTime  @default(now())
  updatedAt     DateTime  @updatedAt
  completedAt   DateTime?                    // проставляется при переходе в done
}
```

Новая миграция Prisma (`add_gtd_item`). Даты (`scheduledDate`) сериализуются в API строками `YYYY-MM-DD` через существующий `formatDate` из `common/date.util.ts` — как везде в проекте.

## Воронка обработки (clarify)

Порядок вопросов при разборе пункта из Корзины (по рисунку пользователя). Каждый вопрос — набор кнопок; ответ либо роутит пункт в корзину, либо ведёт к следующему вопросу.

1. **«С этим надо что-то делать?»**
   - Нет → кнопки: **Заметки** (`reference`) · **В архив** (`archived`).
   - Да ↓
2. **«Делать мне?»**
   - Нет → **Ожидание** (`waiting`); опционально спросить «кому?» → `waitingFor`.
   - Да ↓
3. **«Когда?»** (узел «Сейчас?» на рисунке)
   - **На дату** → **Календарь** (`calendar`), выбрать `scheduledDate`. Дальнейшие вопросы **пропускаются** (календарный трек).
   - **Когда-нибудь** → `someday`.
   - **В ближайшее / делать скоро** ↓
4. **«Одношаговая или проект?»**
   - Проект → **Проекты** (`project`). Пункт становится проектом; под-шаги добавляются отдельно (см. «Проекты»).
   - Одношаговая ↓
5. **«За 5 минут?»**
   - Да → **Сделай сейчас** → сразу `done` (`completedAt` = сейчас).
   - Нет → **Бэклог** (`backlog`).

Каждый переход — это `PATCH` статуса (плюс `scheduledDate`/`waitingFor`, где нужно). Воронка не хранит «промежуточное состояние»: пока пункт не разобран, он просто `inbox`; кнопки процессора вычисляются на фронте по текущему шагу.

## Backend

Новый feature-модуль `backend/src/gtd/` по образцу остальных (`gtd.module.ts`, `gtd.controller.ts`, `gtd.service.ts`, `dto/`, `gtd.service.spec.ts`, мок `PrismaService` напрямую). `PrismaModule` глобальный — импортировать не надо.

Эндпоинты:

- `GET /gtd/items` — все **активные** пункты (все статусы, кроме `done`/`archived`), с `parentId`. Фронт группирует по `status`. Отдаёт плоско: `{ id, title, notes, status, parentId, scheduledDate, waitingFor, order, completedAt }` (даты — строки).
- `GET /gtd/items?status=done` и `?status=archived` — на отдельные вкладки (Done/Архив), по запросу.
- `POST /gtd/items` — `{ title, parentId? }` → создаёт пункт со `status=inbox`.
- `PATCH /gtd/items/:id` — `{ title?, notes?, status?, scheduledDate?, waitingFor? }` → правка/клариф/перемещение между корзинами. При `status=done` сервис проставляет `completedAt`; при уходе из `done` — обнуляет.
- `DELETE /gtd/items/:id` — жёсткое удаление (для реально мусорных пунктов из Архива; обычный «Мусор» — это `archived`, не delete).

Валидация DTO как в проекте (`class-validator`, `@IsOptional` и т.д.). `status` валидируется против `GtdStatus`.

## Frontend

### Навигация

Таб-бар уже расширяемый массив (сделан в Этапе 1). Добавляется таб **«GTD»**. Нынешняя вкладка «Задачи» (обзор `DailyTask`) и «Главный» остаются как есть — GTD встаёт рядом третьим табом. Слияние/переименование — Этап B.

### API-клиент и типы

- `lib/api.ts`: `getGtdItems(status?)`, `createGtdItem(title, parentId?)`, `updateGtdItem(id, patch)`, `deleteGtdItem(id)`.
- `types/api.ts`: `GtdStatus` (union-строка), `GtdItem` (поля как в API выше).

### Экран `GtdScreen` (self-contained, fetch-on-mount, как `TasksScreen`)

Под-навигация по корзинам (сегменты/строка вкладок внутри экрана):

- **Корзина** — на первом месте, с бейджем-счётчиком непустоты (это то, что разбирают в дневном ритуале). Внутри: поле быстрого захвата (добавить пункт → `inbox`) и список inbox-пунктов, каждый с **инлайн-процессором** воронки (кнопки текущего шага; ответы двигают по шагам/роутят в корзину).
- **Бэклог** — список `backlog`-пунктов; можно отметить done, вернуть в Корзину (переклариф), удалить/архивировать.
- **Календарь** — `calendar`-пункты, сгруппированы/отсортированы по `scheduledDate`.
- **Проекты** — список `project`-пунктов; клик по проекту → карточка проекта.
- **Ожидание** — `waiting`-пункты, показывают `waitingFor`.
- **Когда-нибудь** — `someday`-пункты; действие «поднять в Бэклог».
- **Заметки** — `reference`-пункты (просто текст/notes).
- **Done / Архив** — по запросу (ленивый fetch со `?status=`), просмотр и восстановление (PATCH статуса назад).

Общие действия над пунктом (везде): отметить `done`, отправить в `archived`, вернуть в `inbox` (переразобрать), редактировать `title`/`notes`.

### Карточка проекта (рекурсия)

Открытый проект показывает свои дочерние `GtdItem` (по `parentId`), **независимо от их статусов** (часть в Бэклоге, часть в Календаре, часть done). Действие **«добавить шаг»** создаёт дочерний пункт (`parentId` = проект) со `status=inbox` — он попадает в Корзину и проходит воронку как любой другой пункт (рекурсия). Поле `notes` проекта служит местом для подсказок «декомпозировать / с кем обсудить / критерии / первый шаг» (свободный текст, не структурные поля).

### Стиль

Из существующих дизайн-токенов `app/globals.css` и CSS-модулей, как везде. Никакого UI-кита.

## Тесты (TDD)

- **Backend** (`gtd.service.spec.ts`, мок `PrismaService`):
  - `create` — новый пункт получает `status=inbox`, следующий `order`.
  - `getItems` без фильтра — исключает `done`/`archived`; с `?status=done`/`archived` — только их.
  - `update` — смена статуса; при `status=done` ставит `completedAt`, при уходе из `done` — обнуляет; сериализация `scheduledDate` строкой.
  - Создание дочернего пункта проекта — `parentId` проставлен, `status=inbox`.
- **Frontend** (`lib/api.spec.ts`): каждый новый api-метод дёргает правильный путь/метод/тело.
- UI-компоненты не юнит-тестятся (конвенция проекта) — гейт `bun run build`; если группировка/логика шага воронки выносится в `lib/`, она покрывается спекой.

## Не входит в объём (Этап A)

- **Мост «взять в сегодня»** и любое взаимодействие с `DailyTask`/дневным экраном — Этап B.
- **Поглощение/переименование нынешней вкладки «Задачи»** — Этап B (пока сосуществуют).
- **Воскресный крон Weekly Review** — Этап C (реквест зафиксирован в памяти проекта).
- **Приоритет / дедлайн / оценка времени** — Этап C, опционально.
- **Экспорт Заметок в Obsidian** — Этап C, опционально.
- Сферы / YouTube / помидорки — не трогаются вообще.
- Глобальный быстрый захват вне GTD-экрана (виджет/шорткат) — позже; в Этапе A захват живёт на вкладке «Корзина».
