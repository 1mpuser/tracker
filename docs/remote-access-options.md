# Удалённый доступ к трекеру с телефона — варианты (не решено)

**Статус: отложено.** Пользователь попросил зафиксировать варианты и вернуться к решению позже — не разбирать сейчас.

## Контекст

Трекер сейчас доступен только из домашней Wi-Fi-сети (`localhost:4887`, `tracker.performance:4888` через Caddy). Хочется открыть доступ с iPhone откуда угодно (не только из дома). Приложение — single-user, без авторизации по дизайну (см. `CLAUDE.md`: "No auth... Runs only on localhost").

Пользователь сам корректно отметил риск: если открывать порт напрямую в интернет, потребуется добавлять свою авторизацию + rate-limiter против перебора/DDoS — заметно больше работы и постоянный риск (открытый порт = поверхность атаки на домашний роутер), причём избыточно для приложения, рассчитанного на одного человека.

У пользователя уже есть свои домены и сертификаты, которые можно было бы задействовать.

## Рассмотренные варианты

### 1. Tailscale (рекомендация)
Приватная mesh-сеть (WireGuard под капотом) между Mac и iPhone. Телефон получает стабильный адрес Mac'а, доступный из любой сети (сотовая связь, чужой Wi-Fi) — ничего не торчит в открытый интернет, авторизация не нужна: сама принадлежность к личной tailnet — это и есть допуск. HTTPS-сертификаты выдаёт сама Tailscale автоматически (`*.ts.net`), тем же духом, что и нынешний `tracker.performance`-сетап через mkcert — можно переиспользовать существующий паттерн `resolveApiUrl()` в `frontend/lib/api.ts` (сейчас там switch по hostname на `tracker.performance` → same-origin proxy через Caddy), расширив его третьим хостнеймом на `*.ts.net`.

Бесплатно для личного использования. Требует: поставить приложение Tailscale на Mac и на iPhone (аккаунт заводится вручную пользователем — это шаг, который я не могу сделать за него).

### 2. Cloudflare Tunnel + свой домен
Настоящий публичный HTTPS-адрес под одним из существующих доменов пользователя, без открытия портов на роутере (трафик идёт через туннель к Cloudflare). Но раз адрес публичный — обязательно нужен **Cloudflare Access** (бесплатный email-код на входе, проверяется на границе Cloudflare, до того как трафик вообще доходит до Mac) вместо авторизации в самом приложении. Больше шагов настройки (домен должен быть на DNS Cloudflare), но даёт «настоящую» ссылку, которую в теории можно дать кому-то ещё.

### 3. Открыть порт напрямую (не рекомендуется)
Обычный проброс порта роутера в интернет. Тогда обязательно нужны: своя авторизация в приложении + rate-limiter против перебора/DDoS — именно то, чего пользователь сам опасался. Больше работы, постоянный риск, не подходит для no-auth single-user приложения.

## Как вернуться к этому

Когда решение будет готово обсуждать — определиться:
- Нужен ли обязательно «настоящий» публичный URL под своим доменом (→ вариант 2), или достаточно приватного доступа только для себя (→ вариант 1, проще и безопаснее).
- Если Tailscale — после установки нужно будет: (a) добавить его `*.ts.net`-хостнейм в CORS-список origin'ов бэкенда (`backend/src/main.ts`), (b) расширить `resolveApiUrl()` в `frontend/lib/api.ts` третьим случаем по аналогии с `tracker.performance`, (c) решить, использовать ли `tailscale serve` напрямую на порт фронтенда/Caddy или оставить нынешний Caddy-сетап как есть и просто открыть его через Tailscale Serve.
